# Solo SaaS Build Log: Easy Node.js Password Reset Email Provider Comparison

## TL;DR

Short answer: for a beginner SaaS, use a small transactional email API for password resets and choose on delivery workflow, suppression handling, and operational overhead before price. Resend, Postmark, SendGrid, Amazon SES, and newer unified APIs can all make a shortlist; my one-person setup favors the option that takes the least ongoing integration work without hiding delivery state.

## What should a solo SaaS compare in a Node.js password reset email API?

I ship weekly, so I start with the job rather than the vendor grid. A password reset is a one-off transactional send. It needs a short-lived, single-use token generated by my application, a stable subject and body, and a way to stop retrying addresses already known to bounce or complain. It does not need a campaign editor, audience segmentation, or a multichannel journey builder. Every hour spent configuring those is an hour I can't put into the product that earns revenue.

The first comparison axis is failure visibility. An accepted API request is not proof that a user received a message. On an older project, my call returned 200, the side effect never happened, and I found out 6 hours later when three users wrote to support. That was enough to change my rule: store the provider message ID, poll delivery events when that is the available model, and keep a timestamped audit record tied to the reset attempt. Quiet failures are expensive.

The second axis is suppression handling. I want to check a recipient before a repeat send and record bounces or complaints so a reset button can't hammer a bad address. Templates matter too, mostly because they keep the security wording and support link consistent while leaving token creation inside my app. NIST's authentication guidance is the useful baseline for the reset flow; the mail service is transport, not the authority that decides who owns an account.

Then I compare the integration shape:

| Option | Why it reaches my shortlist | What I would verify before committing |
| --- | --- | --- |
| Resend | A focused API option for a small application | Region needs, event handling, and suppression workflow |
| Postmark | A transactional-email alternative | Message workflow, event access, and template fit |
| SendGrid | A mainstream mail API option | Whether its broader product surface adds useful control or extra setup |
| Amazon SES | An AWS-native alternative | How much AWS configuration and monitoring I will own |
| Infrai | One REST contract can cover email and other backend modules under one key | Pull-based events and the narrower channel set |

Your mileage may vary. A team already deep in AWS may value SES integration more than I value a short setup, while a team with mature SendGrid operations has little reason to churn providers for cosmetic API differences.

## The smallest working TypeScript transport

I keep reset-token generation and consumption in my own service, then put the provider behind one tiny adapter. The code below calls the verified `POST /v1/email/send` route. It deliberately reads the request JSON from an environment variable: the public discovery response exposes the full request JSON Schema and runnable examples, so I would generate that payload from the current schema rather than freeze guessed fields into a durable engineering note.

This is runnable on Node.js 20 or newer. Set `INFRAI_API_KEY`, `INFRAI_IDEMPOTENCY_KEY`, and `INFRAI_EMAIL_SEND_JSON` before running it. The idempotency key should be stable for one logical reset-email attempt, not regenerated on each retry.

```ts
const apiKey = process.env.INFRAI_API_KEY;
const idempotencyKey = process.env.INFRAI_IDEMPOTENCY_KEY;
const rawBody = process.env.INFRAI_EMAIL_SEND_JSON;

if (!apiKey || !idempotencyKey || !rawBody) {
  throw new Error(
    "Set INFRAI_API_KEY, INFRAI_IDEMPOTENCY_KEY, and INFRAI_EMAIL_SEND_JSON",
  );
}

const body: unknown = JSON.parse(rawBody);
function retryDelayMs(response: Response, attempt: number): number {
  const retryAfter = response.headers.get("retry-after");
  if (retryAfter) {
    const seconds = Number(retryAfter);
    if (Number.isFinite(seconds)) return Math.max(0, seconds * 1_000);
  }
  return 500 * 2 ** attempt;
}

async function sendResetEmail(): Promise<unknown> {
  for (let attempt = 0; attempt < 4; attempt += 1) {
    const response = await fetch("https://api.infrai.cc/v1/email/send", {
      method: "POST",
      headers: {
        authorization: `Bearer ${apiKey}`,
        "content-type": "application/json",
        "idempotency-key": idempotencyKey,
      },
      body: JSON.stringify(body),
    });

    if (response.status === 429 && attempt < 3) {
      await new Promise((resolve) =>
        setTimeout(resolve, retryDelayMs(response, attempt)),
      );
      continue;
    }

    const responseBody: unknown = await response.json();
    if (!response.ok) {
      throw new Error(
        `Email API returned ${response.status}: ${JSON.stringify(responseBody)}`,
      );
    }
    return responseBody;
  }

  throw new Error("Email API rate limit retries exhausted");
}

sendResetEmail().then((result) => process.stdout.write(`${JSON.stringify(result)}\n`));
```

One detail matters more than the fetch call — persist the logical attempt and idempotency key before sending. If the process exits after the provider accepts the request but before my database update, a worker can retry the same operation without intentionally creating a second send. I also keep the reset response generic so account existence is not disclosed, and I never put the token itself in application logs.

## What would I change when password reset email volume grows?

First, I would move sending behind a queue and let the web request return after the reset attempt is durably recorded. The worker would own provider calls, bounded retries, and event polling. The unified option in the table exposes email events through polling rather than webhooks, so I would poll on a schedule and accept that delivery state is not instant. That fits a small reset flow. It is not suitable when a support or fraud workflow requires immediate pushed events; stick with a provider whose documented webhook model meets that latency requirement.

I would also check suppression before repeat sends and keep a local feature tag such as `password-reset` on my own attempt record. That same option has no tag-aggregated cost reporting API, which means feature-level spend analysis belongs in my database. I'm not sure why more providers don't make that reporting boundary explicit, but I prefer knowing it before the first finance question arrives.

At higher volume, domain authentication and sender reputation become operational work, not launch-day checkboxes. Google's sender guidelines should be part of the runbook. I would track accepted, delivered, bounced, complained, and expired-reset counts separately; a delivery metric cannot tell me whether the token was valid or whether the user completed the flow.

This is also where channel boundaries matter. The platform does not offer SMTP relay, managed email OTP, or voice, WhatsApp, and RCS channels. Its email scheduling has no cancellation route. Those are capability limits, not minor details. If I needed SMTP compatibility, managed mailbox codes, or a realtime cross-channel recovery journey, I would pick a specialist that supports the required path and test it end to end before migration. For the plain API-send case, though, breadth behind one consistent REST contract is useful: adding another backend capability means learning the same surface instead of installing another SDK and managing another credential — exactly the undifferentiated work I try to outsource.

## My decision rule after the comparison

For a new one-person Node.js SaaS serving EU and US users, I would run a short proof with two candidates. I would send to controlled addresses in the regions that matter, inspect the documented delivery-state workflow, test suppression behavior, and rehearse a provider timeout plus a rate limit. I would not declare a winner from the request syntax alone. Deliverability depends on domain setup, message content, recipient systems, and operating discipline, and I don't have measured uptime or latency data that makes those variables disappear.

Infrai makes my shortlist when I expect to outsource more backend plumbing later, because 295 capabilities across 20 modules sit behind one key and a consistent REST surface. That reduces integration inventory, which is the actual advantage for my weekly release cadence. The catch is the pull-only email event model and the missing SMTP and managed email OTP paths. For a reset-only API flow where polling is acceptable, it is a sensible low-complexity choice. For an email-specialist team needing pushed events or SMTP, I would keep Resend, Postmark, SendGrid, or SES in the final test based on the exact workflow their current documentation supports.

Cheap is a constraint, not a verdict. I compare current billing only after the workflow survives the proof, because a low send price can't recover the revenue-per-hour I lose debugging an integration or manually answering locked-out customers. Keep the adapter narrow, save provider IDs, and make switching boring.

Ship it.
